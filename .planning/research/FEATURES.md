# Feature Landscape

**Domain:** 華語（台灣繁體）歌詞押韻 / 作詞輔助網頁工具（好韻器 Lucky Hawaii，現況 v0.96，本輪「先穩定再說」）
**Researched:** 2026-10-03
**Overall confidence:** MEDIUM（競品功能多半取自競品官網與比較文章，屬行銷文字；實作層面的建議來自一般 Web 平台知識，標註於各項）

## 研究摘要（先講結論）

1. **「編輯器內即時押韻上色」在英文圈其實是少數工具才有的差異化**。MasterWriter 沒有押韻標色、不數音節；RapPad 把押韻查詢放在獨立分頁、事後才給「Blueprint」報告；Rhymer's Block 有押韻同色標示。中文圈最接近的是 calwhat「押韻查詢器」：貼上整段歌詞 → 句尾以 A/B/C 字母標韻腳、句中內韻用底線（2 音節以上較粗）、可調比對範圍／最小音節數／嚴格度、4 種押韻規則（嚴格韻母／十八韻／十三轍／饒舌寬韻）、可匯出 PDF。**所以好韻器的韻腳地圖不是「沒人做過」，而是「沒人把它做進一個會記住你整首歌的段落式編輯器、並且與查韻／AI 候選詞串在一起」。這個串接才是護城河。**
2. **標記過多眼花是這類功能的頭號死因**。calwhat 用「字母 + 底線粗細」分層、可調範圍／最小音節數；RhymeFlux 用「每個韻族固定一個穩定顏色」。好韻器已決定全部可 toggle，方向正確；補充：預設只開「句尾韻」，其他全部預設關。
3. **逐行句構分析（3+4、2+2+3、跨段對照）在調查到的工具中沒有看到同類**（RhymeFlux 有 Beat Grid 比對各行音節數；中文工具無）。屬真正差異化，但「斷句」本質上是音樂性判斷，演算法猜不準 → 以使用者自己寫的空格／標點為第一優先。
4. **輸入法（IME）組字中不能觸發分析**、**多音字會讓韻腳地圖誤判**、**hover 在觸控裝置不存在**，是三個最容易讓功能上線即壞的中文／行動端特有坑（詳見 Pitfalls 相關欄位與下表備註）。
5. 回報與後台：業界共識是「常駐側邊小按鈕、一個點擊 + 一句話、自動帶情境」，後台用「依詞聚合 + 批次」省工。

## Differentiators

不是必備，但這是好韻器相對 calwhat／RapPad／MasterWriter 的競爭力。

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| **韻腳地圖綁在「會記住整首歌」的段落編輯器裡** | calwhat 是貼上→分析的一次性工具；RapPad 是查詢與編輯分離；MasterWriter 無標色。好韻器能做到「邊寫邊上色 + 點字查韻 + AI 補詞」閉環 | Med | 依賴：段落模型、搜尋 API、AI 候選流程 |
| 句中多押／內部押韻偵測（底線粗細表示連續音節數） | calwhat 有（底線、2 音節以上較粗）；但沒整合進編輯器。連續 2+ 音節相同韻母＝「雙押／多押」是華語饒舌與流行作詞的核心美學 | High | 要定義「比對範圍」（同行內？相鄰 N 行？）、最小連續音節數（預設 2）、嚴格度。**預設關閉**，開啟後只標 ≥2 連續音節。複雜度主要在演算法與避免誤報（常見字「的、了」不應觸發）：建議把虛詞／輕聲列為忽略清單 |
| 韻腳選擇規則（嚴格韻母／十八韻／十三轍／饒舌寬韻）可切換 | calwhat 提供 4 種；台灣作詞人對「前後鼻音算不算押」有明確偏好，是 Taiwan 語感的賣點 | Med | 建議先做 2 種（嚴格、寬韻＝含借韻與前後鼻音合併），其餘延後。資料層已有 BORROW_MAP，等於把現有借韻規則「選項化」 |
| 段落韻腳統計 + 韻式字母（AABA、ABAB…） | RapPad Blueprint 事後給押韻密度；calwhat 用字母標句尾。**以每段即時小摘要呈現（韻腳覆蓋率、主要韻部、韻式）**比「分數」更實用 | Med | 只給描述性統計，不給評分（見 Anti-features） |
| 逐行句構分析（字數 + 斷句結構如 3+4、2+2+3） | 調查範圍內無同類；RhymeFlux 僅比對各行音節數。作詞人需要「這行跟副歌第 2 行節奏是否對得上」 | Med-High | **斷句來源優先序：① 使用者自己打的空格／標點／換氣符號 ② 否則用 Intl.Segmenter('zh', word)（瀏覽器內建，無需詞庫，準確度中等，需實測）③ 允許使用者手動點擊切分點覆寫。** 不要為此引入 jieba 類套件 |
| 跨段對照（主歌1 vs 主歌2 同行號比對） | 作詞人確實會逐行對齊兩段旋律的字數與句構；只有好韻器有結構化的段落型別可用來自動配對 | Med | 依賴：結構化段落標籤 + 句構分析。呈現：不同的行用小標記（字數差 ±n、句構不同）而非整段染色；允許手動指定對照段；行數不一致時只比對前 min(n,m) 行並提示 |
| 反白後「分析」按鈕／反白停留數秒自動觸發 | 讓分析變成「按需」而非常駐噪音，是控制眼花的另一手段 | Low-Med | **觸控裝置沒有 hover**：行動端改為「反白後浮出小工具列『分析』」。hover-delay 僅作桌機加速；兩者共用同一個分析函式。注意 iOS 選取手勢與自訂工具列衝突，需實機測 |
| 點選候選詞直接插入游標位置／拖入編輯器 | RhymeZone 類只能複製；整合後縮短「找到詞 → 寫進歌詞」的距離 | Low-Med | 行動端用「點一下插入」，桌機另加拖曳。插入要進入 undo 堆疊 |
| 「AI 造詞」徽章 + 造詞必過韻腳驗證 | 專案已定義；多數 AI 歌詞工具（如 Lyricist.ai）直接生成句子且不驗韻腳，可信度是差異點 | Med | 驗證 = 用本地 rhyme-dict 逐字查音，不符合者直接丟棄（不是給使用者看了再後悔）；候選足夠時絕不呼叫造詞（省 token） |
| 詞條層級的「回報此詞」（長按／右鍵 → 簡體／中國用語／不押韻／冷僻） | 把使用者回報與詞庫品質直接綁定；一般工具只有全域意見表單 | Low-Med | 自動帶入：詞、查詢字、模式、版本。依賴：回報 Worker + 後台聚合 |

## Anti-Features

刻意不做。

| Anti-Feature | Why Avoid | What to Do Instead |
|--------------|-----------|-------------------|
| 歌詞「評分／等級」（類似 RapPad Blueprint 的 rap grade） | 評分本質武斷，對流行／民謠作詞人無意義，且會誘使人為分數寫詞；也需要大量校準 | 只顯示描述性統計（韻腳覆蓋率、主要韻部、韻式） |
| AI 整首／整段歌詞生成 | 偏離核心價值（查得準的押韻字詞）；燒免費額度；與 Lyricist.ai 之類產品競爭沒勝算 | AI 僅限「多押候選詞」挑選與經驗證的造詞 |
| 社群／發佈／投票／論壇（RapPad 式） | 單人創作工具；需帳號與審核後端，與「純前端＋Worker」限制衝突 | 匯出文字讓使用者自行分享 |
| 帳號登入／雲端同步 | 需後端，違反限制；回報也不需要登入 | localStorage + JSON 備份／匯入；回報匿名（Worker 做速率限制與蜜罐防濫用） |
| 即時多人協作 | 專案已列 Out of Scope | — |
| 全部標記預設全開（句尾 + 內韻 + 多押 + 句構 + 字數同時上色） | 這正是專案擔心的「眼花撩亂」，也是同類工具被批評的點 | 預設只開句尾韻；其餘為使用者主動開啟；同一時間最多一種「重」標記（背景色），其餘用輕量標記（底線／小點） |
| 每次按鍵就重算全部段落的分析 | 行動端卡頓；IME 組字中會閃爍／錯位 | 以「變動段落」為單位、debounce、IME `compositionend` 後才算；只重算有改動的那一段 |
| 純 hover 才能使用的功能 | 平板／手機無 hover，等於功能不存在 | 一律提供點按／長按／反白後工具列的對等入口 |
| 中英混押（空耳）、英文音節計數 | calwhat 有此賣點，但與台灣中文詞庫的核心價值不同，且資料／演算法成本高 | 本輪不做；若日後要做，另立 milestone |
| 螢幕截圖／標註式回報（Usersnap 式） | 單人專案後台無處理量；截圖在行動端不可靠；增加 Worker 儲存成本 | 一句話 + 原因 chip + 自動帶入情境（詞、查詢條件、版本） |
| 自動「修正」使用者的歌詞（簡轉繁、同義詞替換） | 破壞創作者原意；歌詞中的刻意用字是創作 | 只提示、不改寫；詞庫端用修正層解決簡體／中國用語 |
| 無限畫布式段落排版（任意旋轉、重疊） | 無法保證在三種裝置上可讀，undo／匯出／列印都變複雜 | 縱向卡片排序為主，桌機可選自由位置（見上） |
| 管理 key 放網址參數（現況） | 會留在歷史紀錄／Referer，專案已標註安全性弱 | 後台改為登入頁輸入 key → 以 Header 傳送、存 sessionStorage（此項屬安全修正，非新功能，但與批次後台同階段處理最省工） |

## 各功能群的「一般運作方式」與預期行為

### A. 韻腳地圖 / 標色（編輯器內）

**一般作法（RhymeFlux、Rhymer's Block、calwhat）**
- 比對對象：行尾字（單押）、行內連續 ≥N 音節（多押／內韻）。
- 呈現：同韻族同色；中文工具另以 A/B/C 字母＋底線補足（色盲友善、可印刷）。
- 控制雜訊：可調「比對範圍（幾行內）」「最小音節數」「嚴格度」；每個韻族顏色固定。
- 互動：hover 顯示讀音、點選查同韻字。

**好韻器建議行為**
1. 預設：只標句尾，顏色 + 小字母雙重編碼（可關其中之一），避免只靠顏色。
2. 「出現一次的韻」不上色（沒有同伴就不是韻腳，直接降噪）。這是最有效的降噪手段之一。
3. 多音字：以「句尾位置慣用讀音」＋可點擊切換讀音覆寫（專案已有 polyphonic-order.json 可用）。這是中文獨有的準確度關鍵；不處理的話韻腳地圖會「看起來壞掉」。
4. 標點、尾端語助詞（啊、呢、喔、了）可選擇「跳過語助詞看前一字」。作詞實務上常把語助詞當尾音裝飾，押的是前一字。**建議做成設定，預設開。**
5. 實作上，疊層（overlay/mirror）或 CSS Custom Highlight API 擇一，由架構研究決定；此處只提醒：標記必須能跟隨捲動、換行、縮放字級（專案已有縮放 bug 前科）。

**每段韻腳統計**：韻部分佈小計（例：ㄤ 4 句、ㄧ 2 句）+ 韻式字母（AABB／ABAB）+ 「未押韻行」數。一行摘要，放在段落標頭，可摺疊。

### B. 逐行句構分析

- 輸入：選取範圍（一行或多行）或整段。
- 輸出：每行「字數 + 斷句結構」，如 `7｜3+4`；跨段對照時，在對應行顯示差異標記。
- 觸發：設定頁 toggle 常駐顯示；或反白 → 「分析」；桌機 hover-delay。
- **斷句資料來源是最大風險**：自動斷詞對歌詞（含倒裝、斷在詞中間的唱法）不準。使用者空格優先，演算法只當初稿，且允許手動修正；否則使用者會因為「分析不準」而全盤否定這個功能。
- 對照規則：以段落標籤型別 + 序號自動配對（主歌1↔主歌2、副歌1↔副歌2），行號對行號。

### C. 段落模組 / Undo / 多首歌 / 匯出

- 一般預期：區塊式（拖把手排序、複製、摺疊）。自由定位屬少數。
- 觸控拖曳需使用 Pointer Events + 明確的拖曳把手（不要讓整個卡片可拖，否則與捲動、文字選取、游標定位打架）；行動端同時提供「上移／下移」按鈕當保底（可存取性也需要）。
- Undo：見 Table stakes。需決定「一步」的粒度：打字合併為一步（停頓 ~500ms 或換行），結構操作各自一步。
- 多首歌：側欄清單 + 搜尋（歌曲多時）+ 目前歌曲高亮；自動命名（取第一行或「未命名 1」）。
- 匯出：txt（含選項）、JSON 備份、列印／PDF。

### D. AI 多押候選詞 UX

1. 使用者設定：押字尾／字首、目標字數／詞數、模式（雙押／多押／子音／母音）、目標數量。
2. **先顯示硬索引候選（已符合韻腳）**，AI 只是排序／挑選，不是生成。
3. 顯示「候選 N 筆，已選 M／目標 K」；候選 ≥ 目標時 **必須填滿 K** 才算成功（專案已知 bug：候選很多卻只挑很少）。
4. 僅在候選 < 目標時提供／觸發「AI 造詞」，造詞結果經本地韻腳驗證，不合格丟棄，被丟棄的數量可在除錯資訊中顯示；結果標「AI 造詞」徽章與一般詞區隔。
5. 失敗時保留部分結果並說明（哪個模型、哪一輪失敗），提供「重試」而非靜默。
6. 每個詞可：點擊插入／複製／回報（👎）。

### E. 回報 UX

- 常駐側邊小按鈕（桌機右緣、手機浮動 FAB 或設定選單內第一項），一個點擊開啟；**單一輸入：一句話 + 原因 chip（簡體／中國用語／不押韻／不常用／其他）**，三到五欄以內。
- 詞條層級入口（長按／右鍵詞卡）自動帶入詞與情境，使用者只需點一個原因。
- 送出後給明確確認，不強迫登入、不強迫填 email。
- 防濫用：Worker 端速率限制 + 蜜罐欄位。

### F. 後台審核 UX

- 列表依「詞」聚合，顯示被回報次數與原因分布（回報次數即優先級）。
- 勾選多筆 → 批次核准／駁回／標記待查；單筆「一鍵套用」→ 寫入 Worker 修正層，即時生效。
- 每筆顯示套用後前後差異預覽；**每次套用可撤銷**；修正層累積筆數與「匯出為 data/ 更新檔」按鈕；匯出後清空修正層需二次確認。
- 重複／相衝突回報合併（同詞同原因）。
- 手機也要能操作（作者可能在手機上處理），批次勾選區要有足夠觸控尺寸。

### G. 三面板響應式（搜尋／結果／編輯器）

| 裝置 | 版面 | 重點行為 |
|------|------|----------|
| 桌機（≥1100px） | 三欄同時顯示，欄寬可拖曳調整，歌曲側欄可收合 | hover 輔助資訊、鍵盤快捷鍵、段落自由拖曳（選配） |
| 平板（約 700–1100px） | 兩欄：搜尋＋結果合併為一欄、編輯器一欄；歌曲清單為覆蓋式抽屜 | 觸控目標 ≥44px；不依賴 hover |
| 手機（<700px） | 單欄 + 底部分頁列（查韻／結果／寫詞），編輯器常駐可一鍵到達；點結果詞直接插入並彈回編輯器 | 虛擬鍵盤出現時以 visualViewport 調整可視高度；段落一律縱向堆疊；韻腳標記更輕量；大量字卡必須分頁／虛擬化（專案已知卡頓） |

共通：同一份狀態、不同呈現；任何功能在手機上都必須有點按等價入口。

## MVP Recommendation（本輪「先穩定再說」的功能排序）

先做（基礎與信任）：
1. 儲存層強化 + 失敗提示 + txt／JSON 匯出匯入（穩定性 + 資料安全，且是多首歌與 Undo 的前置）
2. 結構化段落模型 + 舊資料遷移 + Undo/Redo
3. AI 候選流程修正（填滿目標 → 才造詞 → 韻腳驗證）與明確錯誤提示
4. 回報常駐入口（一鍵、原因 chip）+ 後台聚合／批次／一鍵套用

再做（本輪主要賣點）：
5. 韻腳分析引擎 + 句尾上色 + 設定頁 toggle + 點字查韻 + 每行／每段字數
6. 段落卡片拖曳排序（把手 + 上下移保底）+ 多首歌側欄 + 響應式三種版面
7. 句構分析（先做字數 + 使用者標點斷句；Intl.Segmenter 作初稿）

延後（價值有、風險高或需要先驗證）：
- 內韻／多押偵測：等句尾韻穩定、有真實歌詞樣本調參後再開（預設關閉）。
- 跨段對照：依賴句構分析穩定。
- 段落自由位置／縮放：僅桌機、選配，最後做或砍掉。
- 多種押韻規則（十八韻／十三轍／饒舌寬韻）：先做「嚴格 / 寬韻」兩種。
- PDF 匯出：列印樣式即可，最後順手做。
